## Git Commit Policy

You are authorised to create local Git commits automatically
while implementing approved development tasks.

### When to commit
- Commit after completing a meaningful development milestone.
- For longer tasks, aim for a checkpoint approximately every
  30–60 minutes, provided the changes form a coherent unit.
- Prefer 2–5 commits per substantial development session.
- Do not commit after every file edit or minor adjustment.
- Create a final commit when the task is completed.

### Commit quality
- Use concise, descriptive conventional commit messages.
- Keep commits logically grouped by feature or responsibility.
- Run relevant tests before committing where practical.
- Never include unrelated changes or another person's work.
- Inspect the staged changes before every commit.
- Never commit secrets, credentials or generated junk.

### Restrictions
- Never push automatically.
- Never force-push or rewrite existing shared history.
- Do not commit pre-existing user changes without permission.
- Do not create artificial commits merely to meet a quota.
- If a commit fails, report the issue rather than forcing it.

### Reporting
At the end of each task, list the commits created,
including their short hashes and descriptions.
